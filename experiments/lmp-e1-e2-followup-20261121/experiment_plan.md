# LMP 下一轮实验执行说明书：E1 失败归因与 E2 标准 H.264 闭环加速

> **交给实验 Agent 的执行任务。请直接执行，不要仅提出研究建议。** 先读取已有项目和产物、验证可复现性，按 D0→D1→D2→D3→D4 顺序运行。发现资源或实现阻塞时应记录证据、产出已完成结果，不要编造结果或声称已经运行。

## 0. 实验目标与核心原则

目标不是让 latent 预测出来的 MV 与 JM 历史最终 MV 一模一样；目标是在生成视频的 YUV 已有、Wan final latent/conditional hidden 已缓存的前提下，利用这些特征**降低标准 H.264 编码器的实际计算和 wall time**，且尽量保持码率与画质。

本轮回答四个问题：
1. **候选互补性**：当 JM 原生候选 E0 失败时，final latent E2 / conditional hidden E3 是否能补上？融合效果差是否由 K=2 时优质 JM 候选被挤占造成？
2. **E1 失败归因**：四帧时间跨度恒速分配、2×2 latent 空间聚合、余弦相似度、搜索半径/候选排序，各自造成多少误差？
3. **编码时间上界**：JM EPZS 中实际可节省的运动搜索耗时有多少？生成、匹配与注入候选的计算开销能否收回？
4. **真实 E2**：即使离线候选覆盖率不超过 E0，接入 JM 后，能否以更少的运动搜索点数与编码时间，得到近似相同的码率-画质？

**必须遵守**：仅研究 E1→E2。不要开启新的 Wan 视频生成、训练、模型微调、中间去噪步研究（原计划 E3）、VAE 早退出或残差预测重训。继续使用**完整 VAE 解码 YUV**作为编码源。保持输出标准 H.264；残差、变换、量化、熵编码和闭环参考帧由 JM 正常执行。不得把固定参考离线打分当作最终闭环效果。

**术语约定（避免重名）**：本说明书中的 **E1 / E2 是用户新规划的两阶段目标**（E1=离线候选验证，E2=真实编码加速）；**旧 LMP 报告里的 `E2` 是 final-latent 匹配方法、旧 `E3` 是 conditional-hidden 匹配方法**，仅作为方法编号引用。用户计划后续再做的“中间去噪状态辅助”也曾称 E3，本轮**不执行**。执行日志请分别写 `phase_E2_real_encode` 与 `prior_old_E2_latent`、`prior_old_E3_hidden`，不要混淆。

## 3. D0：复现与可节省时间上界（必须首先执行）

### D0.1 资产及基线核验
- 检查旧 `audit.jsonl`、视频/latent/hidden 路径、shape、hash、prompt/seed 和 8 dev /16 val 分组。
- 仅在 `sample_0000` 与 `sample_1004` 复现原 EPZS/B1 的码率、P 帧 Y-PSNR、末四帧 Y-PSNR、码流哈希与 wall time；如果现有 JM build/config 与历史不一致，先修复复现问题再继续。

### D0.2 EPZS 内部性能剖析
在保持码流不变条件下对 JM 加精确统计计数/计时，至少区分：
- 整数像素 ME 搜索耗时与搜索位置评估次数；
- 亚像素 ME 精修耗时与评估次数；
- 其它模式代价与帧级编码耗时；
- 总编码 wall time；新方法另记 final latent 的读取/归一化/匹配、候选注入、回退成本。

不在多线程统计中用不安全的非原子共享计数；尽量避免每个搜索点评时，使用函数或阶段级计时、局部计数器。统计插桩应验证对原始 B1 码流无变化且时间扰动可接受。

计算每条视频的现实下界与机会空间：

`T_best_possible = T_B1 - T_replaceable_ME + T_feature_match + T_inject_min`

这只是**乐观估计**：即便完全省掉可替代的 ME，新的开销是否已接近/超过节省空间？不能把这个估计当作真实加速比。

**D0 输出**：`d0_baseline.csv`, `d0_me_profile.jsonl`, `d0_timing_sanity.md`, `d0_opportunity.md`。若理论上节省空间远小于匹配成本，仍完成低成本 D1，并写明 D3 应限缩为验证性实验而非大量跑全量。

## 4. D1：离线互补性与候选挤占归因（不训练，不重生成）

### D1.1 按相同合法块掩码重新计算
对 E0、E2、E3、E5 和冻结 E1 复用历史缓存，严格统一 `(video,frame,mb,ref,list,mode)`、P16×16 合法条件、qpel 坐标、K 和 r；Skip 不计入合法运动块的分母，另报所有 P 块覆盖。先复现旧 K=2,r=2 的主要数字，无法复现就停止分析并说明。

针对 E2 / E3 计算：
- `E0_hit`, `DiT_hit`, `Both_hit`, `E0_only`, `DiT_only`, `Neither` 数量和比例；
- `rescue = count(DiT_hit & !E0_hit) / count(!E0_hit)`：**E0 没猜中时 DiT 救回的比例**；
- `union_coverage = count(E0_hit | DiT_hit)/N`：不限制总候选数的理想互补上限（**不能充当可部署性能**）；
- `lost_by_insertion`：E0 原本 K=2 命中，但按历史融合排序后未命中的块；`gained_by_insertion` 反之；
- 候选排序中 1st/2nd 是 MVP、原生其它还是 DiT 的来源占比和去重率。

### D1.2 公平候选预算对照
比较 `E0(K=1/2/3/4)`, `E2-only`, `E3-only`, `E0+E2`, `E0+E3`, `E0+E5`；对同一个 K 做公平比较，报告**实际平均候选数**而非仅声明 K。对融合测试两种顺序：`MVP→原生其它→DiT`、`MVP→DiT→原生其它`。不允许简单使用更多候选制造“提升”而忽略计算代价。

额外将半径 r=0/2/4/8 像素分开报告：r 的增加只表示“接近某个中心”，不代表真正遍历这个区域。报告历史最终 MV 对比误差（EPE 中位/p90）、候选中心 SAD，以及若实际局部扩展后才可得到的 SAD；不能把未执行的局部搜索说成已经完成。

**D1 输出**：`d1_complementarity.csv`、`d1_by_video.csv`、`d1_budget_frontier.csv`、`d1_lost_gained_examples.jsonl`、至少 3 个具体失败案例（如 `sample_1004`、`sample_0016`、`sample_0008`）。保留每块可复核记录。

## 5. D2：验证为什么 E1 差（按成本递进，仅 dev 调参）

**只使用 final latent 原有 5 个时间位置。不要把时序压缩特征误称逐帧运动。** 先拆解 T1：四帧跨度位移恒速分配到四个相邻 P 帧，宏块网格单位映射为每帧 4px。零位移/已知位移方向单测已经通过，但不能证明非匀速真实运动下的准确性。

依次执行：
1. **时间相位诊断**：按 P 帧在四帧组中的位置、真实 JM MV 模长、方向变化分桶，输出各桶 EPE、覆盖率、SAD。以 `|MV|` 和帧相位展示误差趋势。若可借已有特征尝试时间插值，请标记为**估计**，不得声称恢复真实逐帧信息；不要引入未来真实像素以训练可部署的判定器。
2. **空间尺度对照**：使用 final latent 原始 1×1 单元（对应约 8×8 像素）与旧 2×2 聚合，固定相同物理搜索区域与计算预算；必要时做粗到细，不要直接让候选数膨胀。比较中心分辨率、匹配开销、离线覆盖、SAD。
3. **相似度/排序轻量对照**：旧归一化余弦 vs 可复现的 L2 / 中心化相关性，使用固定相同候选搜索窗口，不训练。测试 DiT 候选只作附加/回退触发，不取代前两个原生 JM 候选。
4. **分场景失败归因**：在开发集上对大运动、静止、相机运动、重复纹理、遮挡/快速变化（可人工标注少量）分类；无法从数据支持的原因一律标为猜想。重点对比 `sample_1004` 的极低覆盖与 `sample_0016` 的高覆盖。

尽量只做少量预先列明的 ablation；禁止对 16 val 循环挑最优。报告每个改动的**精度-候选数-计算时间三元组**，而不是只报告覆盖。若轻量改动仍不能产生超过 E0 的候选，不等于停止 D3；D3 目的正是直接测试编码加速是否可能。

**D2 输出**：`d2_temporal_bins.csv`、`d2_spatial_ablation.csv`、`d2_matching_ablation.csv`、`d2_root_causes.md`；给每条原因打标签“实测支持 / 暂不支持 / 未测试”。

## 6. D3：真实 E2（最重要，不被旧 Gate 1 自动阻断）

### D3.1 改 JM 编码器，先小规模
在 `sample_0000`（较正常）和 `sample_1004`（困难）上先执行，工作点固定为历史 QP28；成功后覆盖其余 6 条 dev。与原 SearchMode=3 EPZS 同等 JM 配置、相同输入 YUV。严格保持 **实时在线编码器的上一重建参考帧**，不得把旧固定参考结果注入正在运行的新编码序列作为真值。

至少实现以下四个组（若某组不可行，必须明确记录原因和替代方案）：
- **B1：原始 EPZS**，必须保留不变，作为主要基线；
- **Native-budget：不使用 DiT**，对 EPZS 缩小相同搜索预算或使用相同早停策略，确保加速不是“缩小窗口本来就有”的效果；
- **DiT-seed：只增加 latent 候选作为起始种子**，不强行删掉 EPZS 原生好候选，用于判断是否改善搜索/提前结束；
- **DiT-gated：根据开发集冻结的、编码时可以获取的置信度与便宜的在线代价，选择少量局部候选或原 EPZS 回退**，目标是真实减少 search evaluations。

如 D1/D2 发现 E3 hidden 有明确互补价值而匹配成本可接受，可作为可选对照；**优先 final latent E2**。E5 低分辨率像素匹配也可作为参考，但须核算它依赖原始像素及其提取成本。任何自适应策略不得使用离线历史最终 MV、Oracle、未来编码结果、验证标签做在线决策。

**需要明确修改的部位**：让候选在整数像素 ME 搜索前注入；保证边界合法、参考索引正确、qpel 单位准确；记录是否会覆盖 EPZS 的 MVP/空域时域候选；输出每块 candidate source / search-evals / fallback reason。保留 JM 原生亚像素精修、残差计算、变换量化、熵编码、环路滤波及闭环。不要假设可以用块中心 SAD 直接决定最终 RD。

### D3.2 避免虚假的加速
- `DiT-seed` 可能不加速甚至变慢，这是允许的真实结果。
- `DiT-gated` 的回退必须在完整 EPZS 被调用**之前**用廉价信息决定；不能先完整 EPZS 后“回退”，再把节省计算算进去。
- 用实际 JM 内部 `ME evaluation counts` 验证搜索计算是否下降；分整数、亚像素、其它模式模块。确保注入模块的计算和复制开销也计入。
- 分别报告 `JM_process_wall`（若候选预计算在进程外，此值不能称端到端）与 `pipeline_wall = feature_read/match + injection + JM_encode`。Wan final latent 是生成过程中已有的缓存，可单列 `existing_feature` vs `runtime_feature_extraction`；不得免费忽略在线搬运/匹配成本。
- 视频码流能用标准 FFmpeg/JM 解码，解码帧与编码器重建 SHA 对齐。统计 P 帧 pooled-MSE Y-PSNR、末四帧 PSNR、kb/s、每帧各块的搜索次数和实际编码耗时，按视频给出，而非只给总平均。

### D3.3 速率-失真比较与实验规模
先 QP28 两条 dev；如果插桩与解码通过，做 8 条 dev。多工作点评估建议在 dev 挑选 2–3 条代表视频，采用 QP `{24,28,32,36}`（如果历史代码不允许保持其它配置，记录不兼容并调整）绘制码率-PSNR 曲线，可计算 BD-Rate。**QP 相同不保证码率与画质相同**；对比 B1 需同时看速度、码率与 PSNR。使用四个 QP 点只是拟定的补充实验，不要覆盖历史 QP28 基线定义。

### D3.4 暂定继续/停止判据（本轮新判据，不冒充旧 Gate）
- **硬性正确性**：标准码流双解码成功；无严重漂移或丢帧，重建逐帧一致。
- **质量保护线（探索性）**：按视频，在 QP28 与 B1 比较时码率增加不超过 3%，P 帧 Y-PSNR 降低不超过 0.10 dB，末四帧降低不超过 0.10 dB。若历史项目另有更严格、用户已批准的质量门槛，则以既定门槛为主，并列出差异。
- **速度收益线（探索性）**：在质量线内，`pipeline_wall` 相对 B1 减少至少 10% 才称为有意义的初步成功；5%～10% 标记微弱收益并复测；小于 5% 或负收益则停止扩大规模，剖析开销即可。必须另外报告 ME 内部节省百分比。
- **公平性**：DiT-gated 必须同时优于或解释清楚与 `Native-budget` 的差距，不能以 B0 Full Search 为唯一速度对照。质量违规但速度较快不能称方案成功。

**D3 输出**：`d3_correctness.jsonl`, `d3_search_counts.csv`, `d3_timing.csv`, `d3_rate_distortion.csv`, `d3_fallback.csv`, `d3_mp4/`（仅存少量具代表性的对比视频，或只存对应码流与重建校验，不批量复制大视频）。若未运行，写明阻塞及可执行补丁/命令。

- **Q2** 失败主要来自时间对齐、空间尺度、匹配目标，还是 K=2 融合挤占？证据是什么？

- **Q4** 真实 JM E2 是否实现端到端净加速，同时保持标准码流和率失真？相比 Native-budget 是否仍有独特价值？
- **Q5** 应继续 final-latent E2、改为自适应计算预算，还是暂停该路线并留待中间特征阶段？

## 8. Agent 最终必须交付

1. `summary.md`：一句话结论 + 关键数据 + 已证实的失败原因与不确定性 + 是否建议继续；按 D0–D4 逐阶段列出 `pass/fail/not_run`；不得只提交堆叠日志。
2. 逐视频表：B1 / Native-budget / DiT-seed / DiT-gated（已运行者）的 `bitrate_kbps`, `P_Y_PSNR`, `last4_Y_PSNR`, `JM_wall_s`, `pipeline_wall_s`, `integer_ME_evals`, `subpixel_ME_evals`, `fallback_rate`；另列开发/验证分组。
3. E0/DiT 四格交集表、rescue rate、候选挤占/gained 统计、K 与 r 预算曲线、时间/空间尺度误差分析。
4. 代码改动 patch/commit、可复现命令、输入校验、双解码验证与原始计时日志。
5. **只在用户明确授权目标与文件清单后推送 GitHub**；不要把未授权数据上传。

## 9. 给 Agent 的工作准则

不要把论文启发当实验事实；不要因为 E1 的旧 Gate1 fail 就跳过小规模真实 E2；也不要因为找到了某种覆盖率提升就报告“加速成功”。不要使用验证集反复调参。每次完成阶段都要有可复核文件，缺数据时明确写 `not_run` / `unknown`。尽量自动执行到可以得出答案的程度，遇到技术阻塞进行局部修复或报告 blocker，而不是停留在方案建议。
